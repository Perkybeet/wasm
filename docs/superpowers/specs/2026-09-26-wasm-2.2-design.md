# WASM 2.2 - Cero cortes, previews, GitHub y backups fuera del servidor

Fecha: 2026-09-26
Parte de: `../plans/2026-09-26-wasm-to-3.0-plan.md`. Las reglas y decisiones de
`2026-09-25-wasm-v2-design.md` siguen vigentes.

## 1. Blue/green (activación sin corte)

**Hoy**: activar una release cambia `current` y reinicia la unit: segundos sin servicio.

**Diseño**, opt-in por app (`wasm app zero-downtime DOMAIN on|off`, consola en Ajustes →
Releases), solo para apps en releases con proceso:

- Dos instancias con una plantilla de unit con instancia: `<app>@blue.service` y
  `<app>@green.service`, cada una en su puerto (`port` y `port + 1`, reservados al activar el
  modo) y con su propio `WorkingDirectory` apuntando a su release (`releases/<id>`, no
  `current`), así una no pisa a la otra.
- nginx: el `server` de la app apunta a un `upstream <app>` con una sola línea `server
  127.0.0.1:<puerto del color activo>`, escrita en un fichero incluido
  (`/etc/nginx/wasm-upstreams/<app>.conf`).
- Activar: construir la release → arrancar el color inactivo en ella → health gate contra su
  puerto → reescribir el upstream al nuevo color → `nginx -t` y `reload` (sin corte: nginx
  termina las conexiones abiertas con los workers viejos) → esperar un periodo de vaciado
  (configurable, 10 s por defecto) → parar el color viejo. `current` se actualiza al final
  para que todo lo demás (cron, CLI) siga viendo la release activa.
- Fallo del health gate: se para el color nuevo y el viejo nunca dejó de servir. Nada que
  deshacer en nginx.
- Rollback: activar el color inactivo con la release anterior (misma secuencia).
- Apache: mismo esquema con `ProxyPass` a un `BalancerMember` incluido; si resulta frágil, se
  declara solo nginx en 2.2 y se dice.
- Límites: el modo exige que la app aguante dos instancias a la vez durante segundos
  (SQLite con escritura, colas con un solo consumidor, jobs programados en el propio proceso
  no lo aguantan). La consola lo explica al activarlo. Los límites de recursos se aplican a
  cada instancia.
- Migración de una app al modo: se crea la plantilla, se arranca el color con la release
  activa, se cambia nginx al upstream, se para la unit antigua; y al revés al desactivarlo.
  Explícito, reversible, probado en el arnés.

## 2. Integración con GitHub (GitHub App por servidor)

- **Creación**: `POST /api/integrations/github/manifest` construye el manifiesto (nombre
  `wasm-<hostname>`, URL de la consola, callback, webhook URL si hay una pública, permisos
  mínimos: `contents: read`, `metadata: read`, `deployments: write`, `statuses: write`,
  `pull_requests: write`; eventos `push`, `pull_request`, `installation`) y la consola envía
  el formulario a `https://github.com/settings/apps/new` (o de una organización). GitHub
  vuelve a `/integrations/github/callback?code=` en el navegador del operador (funciona por el
  túnel SSH: la redirección es del navegador) y la consola canjea el código en
  `POST /api/integrations/github/manifest/conversions` → id de la app, clave privada PEM,
  secreto del webhook, client id/secret. Todo se guarda en ficheros 0600 bajo el directorio de
  secretos de WASM; nada en config.yaml.
- **Instalación**: enlace a `https://github.com/apps/<slug>/installations/new`; GitHub vuelve
  con `installation_id`, que se guarda. Varias instalaciones (cuenta personal y
  organizaciones) caben.
- **Tokens**: JWT RS256 (10 min) firmado con `openssl dgst -sha256 -sign` por el runner, sin
  dependencias nuevas; canje por un token de instalación (1 h) con `POST
  /app/installations/{id}/access_tokens`, cacheado en memoria hasta 5 minutos antes de
  caducar.
- **Clonado**: fuentes `github:owner/repo` (o URLs https de github.com cuando hay instalación
  que las cubre) clonan con el token por entorno: `GIT_CONFIG_COUNT=1`,
  `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=AUTHORIZATION:
  basic <base64(x-access-token:TOKEN)>`. Nunca en argv, nunca en la URL, nunca en `.git/config`.
- **Asistente**: `GET /api/integrations/github/repositories` y `/branches` para elegir repo y
  rama.
- **Webhooks**: un único endpoint `POST /hooks/github` verificado con el secreto de la app
  (HMAC SHA-256), que despacha push (deploy si hay una app que siga esa rama) y pull_request
  (previews). Requiere URL pública: `wasm web expose-hooks DOMAIN` crea en nginx una ruta
  `/hooks/` de ese dominio hacia la consola en loopback, y solo esa ruta.
- **Estados**: `deployments` y `statuses` de GitHub al empezar, terminar o fallar un deploy.
- Revocar: borrar la integración en la consola borra las credenciales locales y enlaza a la
  página de GitHub para desinstalar la app.

## 3. Previews por PR

- Opt-in por app (`wasm app previews DOMAIN on --domain previews.example.com --max 3 --ttl
  7d`): un dominio comodín ya apuntando al servidor (`*.previews.example.com`), un cupo y una
  caducidad.
- Evento `pull_request` opened/synchronize (GitHub App, o webhook genérico de GitLab/Gitea con
  el secreto de la app) → una app "preview" hija: `pr-<n>.<app-name>.previews.example.com`,
  layout releases, límites por defecto (256 MB, 50 % CPU), sin cron, sin backups, con las
  variables de la app padre salvo las marcadas como solo producción, y su propia base de
  datos solo si la app padre la declara (no en 2.2: se usa la del padre o ninguna; se dice).
- Certificado: uno comodín por DNS no es posible sin API del DNS; se usa HTTP-01 por preview
  (Let's Encrypt tiene cupo de 50 por semana y dominio registrado: el cupo por app lo
  respeta) o un certificado comodín que el operador ya tenga.
- closed/merged → se borra la preview. El TTL borra las abandonadas.
- Con la GitHub App: comentario en el PR con el enlace y el estado, actualizado.

## 4. Destinos de backup remotos (rclone)

- Dependencia opcional `rclone` (paquete del sistema en Debian, Ubuntu, Fedora, openSUSE),
  ejecutado por el runner. Credenciales en ficheros 0600 y pasadas como
  `RCLONE_CONFIG_<NOMBRE>_<CLAVE>` por entorno; nunca un `rclone.conf` legible por otros.
- `wasm backup destination add NAME --type s3|b2|sftp|smb|webdav|drive|onedrive|dropbox|...`
  con las claves de cada tipo (asistente en la consola con los campos de cada backend), `test`
  (lista la raíz), `remove`. Google Drive/OneDrive/Dropbox necesitan OAuth: `rclone authorize`
  en la máquina del operador y pegar el token (guiado).
- Programaciones: cada una elige destinos (local, remotos) y retención por destino. Tras crear
  el backup local se sube con `rclone copyto`, se verifica tamaño y hash, y se aplica la
  retención remota. Fallo → evento `backup_failed` con la salida de rclone.
- Cifrado opcional por destino (rclone `crypt` envolviendo el remoto, contraseña generada y
  guardada 0600, con aviso de que sin ella el backup es irrecuperable).
- Restaurar desde remoto: listar los backups del destino, descargar a staging, verificar,
  restaurar por el camino de siempre (sudo mode).

## 5. Notificaciones de deploy

Eventos `deploy_started`, `deploy_rolled_back` además de los existentes, con la causa del
health gate y el enlace a la consola.

## Pruebas

Arnés: blue/green sin corte medido (una petición cada 50 ms durante la activación, cero
fallos), rollback, fallo del health gate sin corte; previews con webhook firmado local; rclone
contra un destino `local:` y un SFTP en un contenedor. GitHub se prueba con un servidor falso
que habla la API de GitHub (manifest conversions, access tokens, repos) y firmas reales con
openssl.
