# WASM hasta la 3.0 - Plan

Fecha: 2026-09-26
Mandato del dueño: continuar el desarrollo hasta la 3.0.0 (flota de servidores desde una VPS
central), con autonomía total. Documentos: `2026-09-26-wasm-after-2.0-roadmap.md`,
`2026-09-26-wasm-2.0.1-and-2.1-plan.md`, spec `../specs/2026-09-26-wasm-3.0-fleet-design.md`.

Cada versión se publica sola, verificada, antes de empezar la siguiente: suites completas,
E2E (axe, CSP, CLS), arnés systemd con el ensayo de actualización, RPM construido e instalado
sin FastAPI, CI en verde sobre el commit exacto del tag, y una revisión independiente de solo
lectura para cada versión menor y mayor.

## 2.1.0 - Limitaciones de la 2.0 y feedback de producción

- Health check configurable (ruta, códigos, espera) y retención configurable (esquema v9).
- Rehacer el commit exacto de un deploy; aviso de "nada nuevo que desplegar"; rollback a un
  deploy en apps in place (backup ligado al deploy).
- Compose y monorepo con health gate y vuelta atrás.
- `wasm web enable` (consola como servicio de systemd), arranque más claro.
- Inspección rápida (ls-remote + checkout disperso de los ficheros que leen los detectores),
  veredicto de compatibilidad y cancelación real.
- Diagnóstico: certificados caducados, causa de una renovación fallida (A/AAAA), Apache real,
  Telegram con la descripción de la API y buscador de chat id.
- Secretos sin argv (`--stdin`, `--prompt`), SMTP y destinatarios por la API.
- Consola: gráficas con lectura y ampliables, ancho 1600, CLS medido, SMTP y Telegram en
  Ajustes, salud con sus problemas, página de un deploy (reconstruir este commit, fases con
  zona horaria correcta, "no aplica" en estáticas), barra de almacenamiento de backups.
- Licencia AGPL-3.0-or-later.

## 2.2.0 - Cero cortes, previews y backups fuera del servidor

- **Blue/green**: dos instancias de una app en releases (`<app>@blue`, `<app>@green` en
  puertos distintos), el health gate sobre la nueva y el cambio del upstream de nginx con
  `reload`; la vieja se para tras vaciar conexiones. Opt-in por app; el modo actual (reinicio)
  sigue siendo el predeterminado para apps que no aguantan dos instancias (SQLite con
  escritura, colas).
- **Previews por rama o PR**: webhook de pull request (GitHub, GitLab, Gitea) crea
  `<rama>.<app>.<dominio preview>` como release aparte con límites por defecto, TTL y cupo por
  app; se borra al cerrar el PR; el enlace se comenta en el PR si hay token.
- **Destinos de backup remotos** con rclone (SFTP, SMB, WebDAV, S3 y compatibles, Google Drive,
  OneDrive, Dropbox…), por programación, con retención propia, cifrado opcional y restauración
  desde remoto.
- **Notificaciones de deploy** (inicio, éxito, fallo con la causa del health gate, vuelta atrás
  automática).
- **Integración con GitHub (GitHub App propia de cada servidor)**, pedida por el dueño: la
  consola crea la app con el flujo de manifiesto de GitHub (un clic, la app queda en la cuenta
  del dueño y la clave privada 0600 en el servidor), el dueño elige los repos en la
  instalación, y a partir de ahí: selector de repos y ramas en el asistente (privados
  incluidos), clonado con tokens de instalación de 1 hora pasados por entorno
  (`GIT_CONFIG_*` con `http.extraHeader`, nunca en argv ni en la URL), webhooks de push y PR
  configurados solos, estados de deploy en GitHub y comentario con el enlace de la preview en
  el PR. Permisos mínimos: contents read, deployments/statuses write, pull requests write
  (comentarios), metadata read. JWT RS256 firmado con `openssl` por CommandRunner (sin
  dependencias nuevas). Los webhooks necesitan una URL pública: publicar solo `/hooks/` de la
  consola en un dominio del servidor mediante nginx, opcional y explícito. GitLab y Gitea
  (OAuth) después.

## 2.3.0 - Llegar antes y en español

- **Español** en la consola (catálogos tipados, `Intl`), las notificaciones y el CLI; test que
  falla con una clave sin traducir; axe/E2E en ambos idiomas.
- **Recetas** sin Docker: WordPress (PHP-FPM), Ghost, Umami, Uptime Kuma, n8n, Plausible.
- `wasm import --from vercel|railway|coolify` (propone la configuración en el asistente) y
  `wasm export`.
- Datos de ejemplo neutrales en la semilla de desarrollo y en las capturas.

## 3.0.0 - Flota

Según el spec: nodos por SSH con túnel a la API en loopback de cada nodo, proxy de API y
streams en la central, sudo mode aplicado en la central con la lista de rutas que publica cada
nodo, cabecera de actor para la auditoría, selector de servidor y página Flota en la consola,
`wasm --node` y `wasm fleet status` en el CLI, arnés con dos contenedores.

## Riesgos

- Blue/green toca el camino más delicado (activación); se entrega opt-in y con el arnés.
- La flota concentra credenciales root-equivalentes en la central: documentado, revocable desde
  cada nodo, y con sudo mode y auditoría en ambos lados.
- El español multiplica el texto a mantener: el test de claves y un único catálogo lo contienen.
